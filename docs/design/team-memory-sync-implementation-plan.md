# Team project memory sync

Reviewed against Rovik commit `fd877244`. This revision replaces the attached revision 2.0 for implementation planning. The hub-as-replica design fits the current workspace. The existing exchange solves record convergence. Team membership, publication consent, team-scoped deletion and recovery require new code before a team can use it.

## Replication boundary

Use one SQLite store per project on a single HTTPS hub for the initial deployment of roughly 100 developers. Register a hub service and a reusable team client in the workspace in `src-tauri/Cargo.toml`. Keep HTTP, credentials and scheduling outside the memory crate. Start with the desktop as the team publisher. Daemons keep using the existing personal-host exchange and headless evaluations keep team sync off.

**Keep team epochs and stamps in a separate local replica.** A desktop store already exchanges whole-project epochs with its owner's hosts. Its apply path deletes all records and change rows for a higher epoch, and accepts remote-origin changes for onward export. Filtering the outgoing team page alone cannot isolate a team clear, a personal-host clear, or two different payload projections with the same stamp. Use a per-link SQLite replica for the sanitized team view, beside the ordinary app store. The hub and this replica can then use the existing whole-project epoch semantics. Private and unsent work stays in the app store. This replaces the draft’s selective epoch wipe and shared-ID sidecar design.

Build a bridge between the app store and the team replica:

1. Before first publication, preview eligible records and ask the developer which existing history to share. Persist the choice and link. A fresh link initially pulls team memory. Re-link and policy changes require the same explicit handling of history.
2. Observe material app changes using a durable local cursor. Project approved content into the team replica as local writes so that its stamps describe exactly the bytes it sends. Maintain a durable per-link mapping of app ID, team ID, last projected content, last imported revision, publication state and authenticated attribution. Protect shared state by project and link. A matching ID alone proves neither identity nor consent.
3. Import team changes into the normal store through a bridge operation that preserves local counters and local-only tags, remaps IDs and references, and recalculates applicability. Preserve claim-scoped verification only when it still describes the projected claim. Journal intent before crossing database boundaries, replay with a stable operation ID and persist the completed mapping before advancing progress. Make repeated imports and unchanged projections no-ops. Test process termination between every commit.
4. Record the last common revision. If an incoming edit, tombstone or epoch supersedes a locally modified shared record, preserve its pending content in a recoverable conflict entry before applying. A team clear removes only mapped team material from the app view. A personal clear, prune or daemon-origin tombstone must never become an administrative team clear or an implicit team deletion. Expose explicit authorized team withdrawal. Retain a durable receipt for withdrawn IDs and prevent accidental re-publication after reconnect.
5. Define visibility on personal hosts during linking. App records can travel to registered hosts through the existing personal exchange. If project policy forbids that onward transfer, block linking until host-bound filtering covers those records and handles existing copies. A team import that returns via a personal host must retain its mapping and must not acquire local authorship. Unknown-origin personal-host edits require review before publication.

## Store changes and compatibility

Start by exercising the existing merge. Add the smallest format-compatible APIs needed by both hub and bridge, with corresponding `SharedMemoryStore` wrappers.

- Expose per-change validation and bounded export results carrying scanned sequence, skipped ID and reason. Oversized or malformed records must not wedge the queue. Keep durable rejections, retry corrected revisions, and advance only through scanned input whose disposition is durable. Enforce byte, item, string and counter limits before mutation, including stale pages. Preserve headroom for local clock increments.
- Separate the shared-content update from local applicability and usage changes. Validate a verified incoming claim against its claimed hash. Derive applicability for the receiver using the existing file fingerprint, after checking restricted paths. A mismatch requires revalidation. Missing or unsupported fingerprints give unknown applicability. Read files outside SQLite transactions. Recheck before use when checkout content changes.
- Review generation fencing in `sync_apply` and the bridge import path. Today an accepted update to an existing row, a deletion or a newer epoch bumps the generation. Keep cancellation for changes that invalidate in-flight work. Test a concurrent agent write and embedding backfill before narrowing the fence for metadata-only changes.
- Add explicit link-scoped cursor reset and replica-replacement handling. Existing `sync_ack` takes maxima for the same replica. Quiesce the link during reset. A cloned or restored writer must acquire a new identity, reconcile accepted revisions and reissue pending edits with fresh stamps. Never rotate the personal store to repair a team link.
- Use separate version numbers for the team envelope and its SQLite schema. Introduce a store v5 migration only for persisted changes to the existing v4 store. Replace affected triggers explicitly, since `CREATE TRIGGER IF NOT EXISTS` preserves old definitions. Keep legacy callers working and test existing v4 files and old-format host pages. A migrated file needs a backup for rollback to a v4-only binary. Team-only tables can live in the team database.

## Team service and client

**Exchange.** Authenticate each request and authorize its project before opening a store. Readers may pull, editors may publish eligible revisions, and admins may clear or purge. Bind devices and writing replicas to principals. The team replica can relay hub stamps during export. Accept an exact known echo idempotently, and reject newly asserted changes using another writer’s stamp. Verify authorization, epoch, size, clock, paths, projection and evidence before apply. Write the accepted revision, authenticated author or verifier, audit event and idempotent outcome atomically. Serialize conflicting changes per project. Keep credentials in the platform key store and audit metadata free of secrets.

**Progress.** Exchange the expected hub identity, last committed receive cursor and bounded push page for per-change outcomes and a pull page. Preserve rejected or conflicting edits locally. Save the response disposition and applied pull before acknowledging. Retry transient failures with jitter and respect server backoff. A replica change restarts discovery. A stale epoch stops pushing until the client has preserved pending edits and reconciled the new epoch. Return actionable status for revoked access, required upgrade and blocked records.

**Bootstrap.** Stream ordinary bounded pages over HTTPS with header, replica, epoch, per-page cursor and completion trailer. Include tombstones. Persist each committed page and resume after interruption. Track bootstrap completion explicitly so an empty project with cursor zero completes once. Pin the identity and epoch for a stream, restart reconciliation if either changes, and validate a digest on each completed stream segment. Catch up concurrent writes using normal pulls. Exercise resume, clear during stream, duplicate delivery and interrupted finalization. Defer portable offline bundles.

**Publication policy.** Begin with opt-in project facts and procedures backed by user assertions, code observations or tests. Keep episodes and provisional deductions local by default. Block private tags, restricted files, invalid paths and secret matches before enqueue and enforce server-side validation independently. Inspect title, content, evidence, tags and paths, strip local usage data and chat tags, and clear references to unpublished episodes. Flag failures without logging the matched value. Re-evaluate pending items on policy changes. For material already shared, expose withdrawal and explain retention of prior copies. Preserve independent private episode retention while preventing personal pruning from deleting shared history.

**Integration.** Use the existing project settings and memory manager for link preview, pause, sync now, last successful exchange, blocked records, conflicts and provenance. Distinguish the authenticated author of a claim from a later editor or verifier. Serialize exchanges per link, use blocking workers for SQLite, and keep network waits off the retrieval path. Add wakeups for local changes and reconnect plus periodic catch-up. The project memory enable/capture settings already have separate meanings. Introduce team opt-in independently.

## Provider and account decisions

GitHub.com and GitLab.com are the initial identity providers. Repository accounts belong in application settings so a developer can sign in before opening a project. Keep one credential per provider in the desktop secret store. The initial device flow requests identity scopes. Future pull-request or merge-request actions can reuse the backend account API and request additional permission when needed.

For team sync, the hub issues a separate, expiring session. The operator registers the numeric repository ID for each project and opts into onward replication to personal hosts. The hub checks membership for the signed-in provider account and binds the device to that account. See the [deployment and recovery guide](../team-project-memory.md).

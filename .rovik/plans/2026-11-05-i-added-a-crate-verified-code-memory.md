# Wire the project's long-term memory into the agent

`src-tauri/crates/verified-code-memory` exists but nothing uses it: it isn't a workspace member, no crate depends on it, and the agent never reads or writes it. Make it a member, open one `SharedMemoryStore` per project under the app's data folder, and use it at the four points of a run — recall at task start (into the prompt and a "Relevant prior work" panel), file-specific hints before an edit, promotion or invalidation after the checks, and the outcome plus a structured reflection at the end. A new Settings → Long-term memory page (in the project group) shows the project's memory count and a checkbox that switches the feature off for that project.

7. Promote or invalidate after the checks

## Decisions

- The switch is per project, in `project-settings.json` (key `memory`), because the block shows that project's own count and the run reads the same settings file at prepare time, as it does for checks and restricted files. Absent means on.
- One database per project in the app's data folder (`data/memory/<project_key>.db`), not inside the user's repository, per your answer: nothing is written into the project, and the file is keyed like the overlays' per-project folders.
- Inline hints reuse `ToolNote` (already rendered as the call's note while it runs) instead of a new event and a new component.
- One event, `memoryRecalled`, replaces the chat's list: the run's start sends it, its end sends it again with verification, evidence and `helped`. The panel is the single UI surface for your points 1, 3 and 4.
- Deprecation needs evidence: only a failed check whose `error_files.changed` names one of the memory's own files deprecates it; anything else failed but not proven guilty keeps its state and only records a failed outcome. `status == "preexisting"` isn't a failure here, so a failure the change didn't cause can't invalidate anything.
- The reflection is structured (outcome, changed files, checks), never "I finished"; a lesson becomes a procedure only when the run repaired a failing check itself, and a newer one supersedes the older with `resolve_conflict`.
- `Run`'s memory work runs in `crate::rt::spawn_blocking`: the store is SQLite and must not block the async runtime.
- A store that can't be opened logs and yields nothing: memory never fails a run.

## Risks

- Retrieval falls back to the project's most recent memories when full-text search finds nothing, so a weak match can reach the prompt. The limit of 8 and the "provisional" badge keep it visible; it is worth watching whether the fallback should be dropped for runs.
- Deprecation still rests on a heuristic (the failure's file is the memory's file), so a memory about a file the run touched for another reason can be invalidated wrongly. It is recoverable only by hand in the database.
- The panel stays after the run ends until the chat's next run replaces it; there is no dismiss.
- Memory is per project folder, so an isolated chat and its project share one file while each chat's changes differ; a memory promoted in a chat that is later discarded stays.
